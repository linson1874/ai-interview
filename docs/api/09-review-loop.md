## 0. 本版范围（一句话产品定义）

把"被评过分的错题"变成"按遗忘曲线回来的复习任务"：错题入队 → 到期出现 → 复习判分 → 间隔更新 → 掌握度曲线。**追问决策器（CAT-lite）不在本版**——那是 D1 裁决里的第二幕，等本版 v1.0 后开机。

## 2. 决策点

### 🔶A 复习单元与材料来源（#36 的续集）
错题的"题"以什么为身份：面试场次里的原题（t_interview_question 行）还是能溯源到的题池行（evidenceKbId 映射）？复习时的开卷材料用哪个：07 评分时产出的 refAnswer（贴着用户答案写的，质量高）还是题池 answer_text（经过人工审核，口径稳）？两条路线各自的坑（提示：一场"项目题"很可能根本没有题池祖先；而 refAnswer 未经审核——**它过没过 08 §8 那套评测卫生吗？**）拍板并写清映射失败时的降级路径。

身份：复习单元 = t_interview_question 行（场次原题）
evidence 现成指它、业务全覆盖、上下文自带。题池映射降级为可选增强：复习单元表加一列 kb_question_id（nullable，尽力而为地填——复用 ask 同一条检索链，top1 且 d≤0.3 才记，失败留空）。掌握度曲线按 kb_question_id 聚合（有则多场并一条），无则按场次行独立成线——身份是场次行，聚合键是尽力而为，去重债留给算法设计（决策点 A 的 ZSET score 天然处理到期，不在身份层硬解）。
材料：三级阶梯，降级必标注
kb_question_id 存在且 answer_text 非空 → 用 answer_text（审核口径，V5/V6 实证过的正宫）；
映射失败或 answer_text 空 → 用 refAnswer，材料头部明示："本参考答案系评分时 AI 生成、未经人工审核"——08"（本题无答案段，仅题干）"同款句式：诚实标注，绝不静默把未审核冒充审核；
两者皆空 → 裸题干 + 明示，且入队时 Java 侧硬校验：题干非空 + 两材料至少其一非空，全空=脏数据不配进复习队列。
降级路径（映射失败时，写死三条）
映射失败 ≠ 复习失败：降级只降材料等级，复习单元照常成立（身份锚不依赖题池——这是与 08"检索空手→拒答"的关键区别，那边材料即答案来源，这边材料只是辅助）；
每次降级记一条日志（qid、缺什么、用了什么替代）——v1 不上表，日志先跑，给导师攒"哪类题老映射不上"的数据；
项目题反复错的出路不开后门、开正门：同类错题攒到一定频次，馆长手工审核入池（source=review-mined，走 draft→approved 同款流程）——08 的审核闸哲学原样延续：想让一份材料进模型嘴，唯一的路是过人工审核，复习链也不例外

### 🔶B 间隔算法与参数位置
Leitner 五盒（对→下一盒 1/3/7/16/35 天，错→回第一盒）vs SM-2 简化（EF 系数×重复次数弹性间隔）。二选一拍板，三条附答：① 半对（判分 3/5）走前进还是原地？② 全部参数进 application.yml（旋钮进 Git 家法，AGENTS 在案）；③ 给出一条"为什么这个选择配得上 12→300 题的规模"的论证——算法精细度要匹配数据量，SM-2 在没人肉校准的 EF 上是玄学，这句话你可以同意也可以反驳。

Leitner 五盒。SM-2 判"数据量不配"，不是判"算法不好"——这句话面试要原样说。
附答① 半对（score=3）：原地不动。 完整三档规则：≥4 前进一盒；≤2 回第一盒；=3 原地冻结。理由不是和稀泥，是信号质量：只有语义明确的信号才配驱动状态转移——4/5 分模型判"会了"可信，0/1/2 判"不会"可信，3 分是 LLM 判分方差最大的中档，用最不稳的信号去挪盒子，等于让噪声写调度。冻结的另一个红利：连续两次 3 分的题会滞留在低盒反复到期——这恰好是我们想要它多练的行为，惩罚了"半懂"，但用的是停留而不是降级，规则诚实。

### 🔶C 推送通道与复习语义（**本项目第一个纯产品决策，评审语义归你，我只守一致性**）
(a) 独立复习面 `GET /review/today`；(b) 新建面试时混入"热身 3 题"；(c) 两者。必答的子问题：复习判分**算不算当日面试样本**（07 J4 样本闸与 overall_score 的口径会不会被复习题污染？——你写过那条"宁缺毋滥"条款，现在轮到守住它）；复习结果要不要进报告（进=报告口径变化，需 07 升版；不进=闭环断在半路）。**这条决策的每个选项都要写出它对 06/07 合同的影响面——契约影响分析（CIA），从今天起是你的标准动作。**


选 (c) 的语义、(a) 的顺序——分两阶段：

子问题裁决（v1/v2 分期写明——**F1 执法：v1 说"06/07 零升版"就不许同时给 06 的表加列，两阶段通用是话术，分期才是设计**）

### 🔶E 队列可靠性：06 家法平移（这道题答好了，面试讲半小时）
`ZPOPMIN` 弹出即消失——进程死在判分中途，复习任务人间蒸发。本系统的既有答案：**peek（ZRANGEBYSCORE 0..now LIMIT n）→ 处理 → 成功后 ZREM + 更新下次 score 回队**。但还有第二问：捞起的任务正在判分时，另一个调度轮次把同一条又捞了怎么办（06 抢单问题的 ZSET 版）？——把 06 的哪件家法平移过来？（剧透：CAS 的思想不只在 MySQL 里能用，`ZADD GT`/状态字段/先占后做都行，选一个并说明它对应 06 的哪个原型的哪个场景。）in-flight 的"PEL 超时回收"要不要？12→300 题的规模下你的答案。

主链：peek 三步，v1 不加认领层
1. peek:    ZRANGEBYSCORE review:due:{userId} 0..now LIMIT n   ——不删除
2. 判分:    07 评分链内部复用，事件写 t_review_log，盒号+新 next_review_at 写 MySQL（先账本）
3. 回队:    ZADD GT score=新到期时刻                            ——后投影；ZREM 都不需要，改 score 即回队
顺序家法：先更新账本、后更新投影——投影滞后可以重建，账本滞后无人能补（06 outbox 的同款判断）。
抢单问题的裁决：设计入约、机制不提前付费
v1 单实例 fixedDelay 串行，抢单场景不存在，不加认领。但 09 正文写明升级路径与触发条件：
触发条件：调度多实例化 / 复习判分改走 Stream 异步（那时 06 的整套家法连锅端）。 升级方案：Lua CAS 租约——peek 后 if score==旧值 then score=now+lease（真 CAS，不用 GT 的"更大就覆盖"），处理完 ZADD GT 新间隔；租约到期自动可被再捞。 06 原型对应：PEL min-idle sweep（"别人领了活死了，600s 后抢回"）——租约 score 就是 ZSET 版的 min-idle 时钟，把"领了活"写进 score 本身，回收就不需要独立清扫器。这是 06 里 sweep 和恢复模式两个机制在 ZSET 语义下的合并形态。
（若导师觉得"不存在的问题"也要防——比如未来某天有人把 fixedDelay 手滑改成 fixedRate——备选是最便宜的 MySQL 状态字段方案，claim 两列入 t_review_item。我的反对理由：为未发生的部署形态付列税，且幂等的真防线在判分侧不在调度侧，见下。）
PEL 超时回收要不要：v1 不要，理由三条
peek 无认领 → 无"认领者死亡"状态 → 无物可回收（机制没有服务对象）；
我们唯一的死亡形态是"自己死了"，恢复=重启后下轮 peek 自然再捞——恢复模式（06 原型①）在 peek 模式里是免费的，不需要 XAUTOCLAIM 那样的显式实现；
投影级故障（Redis 数据没了）由启动全量重建兜底（06 原型③ NOGROUP 自愈平移），300 题的重建成本 O(300) 毫秒——规模未到逼出增量对账的时代。
补一条真防线（比认领更根本）
**F2 执法（"干脆接受"半句废除）**：曲线均值可稀释，**盒号双跳不可稀释**——用户连点两次=同一题前进两盒，调度崩溃重捞=再判一次，这不是失真，是把状态机推离它该在的位置。防线两条转正为必做件（不是可选项）：
① **用户侧提交 CAS**：POST /review/answer 先 `UPDATE t_review_item SET status=processing WHERE id=? AND status=due`，0 行=该题正在复习（code=1 文案走 S13 家法不静默）——这是 06 抢单 CAS 第四次转世，这次防的是浏览器双击；
② **判分侧快照比对**：回写盒号前 `last_review_at` 相邻重复检测（一行 WHERE），调度器崩溃重捞与用户双发共用这条兜底。
"把并发伤害压到可稀释"哲学保留——但它的完整形态是**稀释+幂等两道**，只留前者叫半句话。W5 期望随之改写：双发=一判一拒，账本无重复事件、盒号单跳。
