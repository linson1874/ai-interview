## 2. 决策点

### 🔶A 复习单元与材料来源（#36 的续集）
错题的"题"以什么为身份：面试场次里的原题（t_interview_question 行）还是能溯源到的题池行（evidenceKbId 映射）？复习时的开卷材料用哪个：07 评分时产出的 refAnswer（贴着用户答案写的，质量高）还是题池 answer_text（经过人工审核，口径稳）？两条路线各自的坑（提示：一场"项目题"很可能根本没有题池祖先；而 refAnswer 未经审核——**它过没过 08 §8 那套评测卫生吗？**）拍板并写清映射失败时的降级路径。

### 🔶B 间隔算法与参数位置
Leitner 五盒（对→下一盒 1/3/7/16/35 天，错→回第一盒）vs SM-2 简化（EF 系数×重复次数弹性间隔）。二选一拍板，三条附答：① 半对（判分 3/5）走前进还是原地？② 全部参数进 application.yml（旋钮进 Git 家法，AGENTS 在案）；③ 给出一条"为什么这个选择配得上 12→300 题的规模"的论证——算法精细度要匹配数据量，SM-2 在没人肉校准的 EF 上是玄学，这句话你可以同意也可以反驳。

### 🔶C 推送通道与复习语义（**本项目第一个纯产品决策，评审语义归你，我只守一致性**）
(a) 独立复习面 `GET /review/today`；(b) 新建面试时混入"热身 3 题"；(c) 两者。必答的子问题：复习判分**算不算当日面试样本**（07 J4 样本闸与 overall_score 的口径会不会被复习题污染？——你写过那条"宁缺毋滥"条款，现在轮到守住它）；复习结果要不要进报告（进=报告口径变化，需 07 升版；不进=闭环断在半路）。**这条决策的每个选项都要写出它对 06/07 合同的影响面——契约影响分析（CIA），从今天起是你的标准动作。**

### 🔶D 数据形状与引擎归属
`t_review_item` 与 `t_skill_profile` 放 MySQL 还是 PG？（双引擎分工复试题，答"看心情"的直接退回：调度状态是事务数据→？）；t_skill_profile 的粒度：按 08 E1 的哪条轴聚合（tags 方向轴还是 category 题型轴——复习掌握度对用户呈现时，"MySQL 62%、Redis 41%"和"八股 58%、项目 70%"哪个才是想进步的人看的？或者两轴都要，各算各的）；sql/07 增量脚本你自己写（第三个 MySQL 脚本+第二个 PG 判断，引擎选择写进脚本注释）。

### 🔶E 队列可靠性：06 家法平移（这道题答好了，面试讲半小时）
`ZPOPMIN` 弹出即消失——进程死在判分中途，复习任务人间蒸发。本系统的既有答案：**peek（ZRANGEBYSCORE 0..now LIMIT n）→ 处理 → 成功后 ZREM + 更新下次 score 回队**。但还有第二问：捞起的任务正在判分时，另一个调度轮次把同一条又捞了怎么办（06 抢单问题的 ZSET 版）？——把 06 的哪件家法平移过来？（剧透：CAS 的思想不只在 MySQL 里能用，`ZADD GT`/状态字段/先占后做都行，选一个并说明它对应 06 的哪个原型的哪个场景。）in-flight 的"PEL 超时回收"要不要？12→300 题的规模下你的答案。
