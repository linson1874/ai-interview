## 3. 决策点

### 🔶H1 消息体里放什么
候选 A：只放 `interviewId`（消费者从 DB 取数）；候选 B：塞整份简历文本。从消息体积、DB 一致性（发送后简历被改了呢）、排障可读性三个角度论证，不许只说"我习惯 A"。
只放A，论据：消息体积：B 塞整份简历 = skills 1024 + self_intro 1000 + 其余 ≈ 2-3KB 每消息；Stream 是要存历史全量的（不像队列阅后即焚），胖体的成本按投递次数×保留长度累积，重投/H5 retry 场景还翻倍。A 是 8 字节。
DB 一致性：这是真正的胜负点——B 是快照语义（按发送时刻的简历出题），A 是读时语义（消费者开工瞬间查最新简历）。推演两个场景：正常首发，两者只差零点几秒，无意义；retry 场景（用户失败后点了重试、甚至先改了简历再重试）——A 用最新简历出题恰好符合用户期待（"我改了简历，重新出吧"），B 的旧快照语义想要正确就得引入序列化快照存储，复杂度爆炸。更根本的：消息体放线索不放行李 = 单一事实源纪律——导师拿它治过配置、治过登录逻辑，现在轮到治消息。

**导师 R5 批注（v1.1）**：本段结论经实战检验反而更硬了——count 窟窿（见 §6 R5）之所以能一列修好，正因为消息体是纯线索。若当初选 B，今天坏掉的不是 count 一个字段，是"参数只有一个家"的纪律。
排障可读性：XPENDING/XRANGE 肉眼可读（ID=12 → 直接查库定位现场）；B 是 3KB blob 糊在终端里。附带安全分：简历含真人姓名等 PII，塞进 Redis 流=在明文、长期保留、没访问控制的地方存个人信息。

### 🔶H2 消费者形态
单进程内几个消费线程？group 名、consumer 名怎么定（重启后名字漂移会留下什么孤儿 PEL？提示这条和 H4 的 XAUTOCLAIM 有牵连，想一想再答）。
单线程、名字必须跨重启稳定
消费线程 1 个起步。论据：一天几场、每场 30-60s 的负载，单线程吞吐上限≈60 场/小时，撞不到；多线程扩容的前提是每线程一个独立且固定的 consumer 名，留作阶段三后段的可选项而不是第一版复杂度。
group 名 gen-group，consumer 名 gen-consumer-1——硬编码常量，绝不用时间戳/UUID。导师这条提示的实物就是你预习实验里的场景：名字漂移 = 每次重启造一个新 consumer，重启前那个名字在 PEL 里的挂账永远没人认领（"我"已经不在了，没有进程知道用旧名去 XREADGROUP 具体 ID 恢复），账本只增不减，最后全靠 XAUTOCLAIM 超时兜底——那是给架构 bug 交税。固定名 = 重启后的进程拿回自己的账：启动时先按"恢复模式"处理自己 PEL 里的存量（读 XREADGROUP 用具体 ID 而非 > 的那发文档，H2 的完整答案在那），处理完再进 > 正常消费。

### 🔶H3 幂等门（本版灵魂，答错全楼歪）
消费者拿到消息后，用什么 SQL 保证"同一个 interviewId 的生成只发生一次效果"？写出那条语句的形状（提示：UPDATE 的 WHERE 里有什么、影响行数说明什么），并回答：抢输的那个消费者该 ACK 还是留 PEL？为什么。
UPDATE t_interview SET status = 1
WHERE id = #{interviewId} AND status = 0
WHERE 里有前置状态：一条 UPDATE 原子地完成"检查+占坑"（数据库行锁帮你 CAS），这就是分布式锁的最低成本形态。不许写成"先 SELECT 判 status 再 UPDATE"——查改之间的间隙里两个消费者都能通过检查，这是经典 check-then-act 竞态。
影响行数说明一切：1 = 抢到活，去调 AI；0 = 这活已有人干（或状态不对），别调。
抢输者 必须 ACK。理由回到 PEL 的语义：PEL = "这个消费者还有活没干完"。抢输的消费者的"活"就是确认坑被占了——确认完=干完了，不 ACK 等于把一个永远做不完的活挂在自己账上，它会：① 被下次 XAUTOCLAIM 再夺回 → delivery count 无意义攀升 → 最终被 H4 误判成毒消息处死，冤案就是这么造出来的。

**导师 R1 修正**：你这条 SQL 的形状完全对，但 `SET status=1` 用错了目的地——1 在状态机里是"题目就绪、用户可作答"的业务态，拿来做"抢单"技术态，就会出现 T2 轮询里 `status=1 但题目是空的` 的窗口期（前端会以为生成完成）。修正后抢单翻 **0→4**（生成中已认领），完成时另有 4→1 那条边。你的原子 CAS 思想原样保留，只是给它配了一个诚实的状态值。

### 🔶H4 毒消息与死信阈值
delivery count 超过几次判死刑？判死刑的动作清单（DB 状态、ACK、日志级别）写全。XAUTOCLAIM 的 min-idle-time 定多久——和"AI 一次正常调用要 30-60s"摆在一起算，别把活人误判成僵尸。
 毒消息判死刑 + min-idle 算术
阈值：delivery count ≥ 3。账：正常 1 次；消费者崩溃恢复 +1=2 次；第 3 次还失败说明不是偶发而是环境性/代码性故障，止血。AI 瞬时抖动不该烧到这个数——因为 L3 重试在进程内已吸收，烧到 Redis 层的重投只剩基础设施故障。
判死刑动作清单（四条，缺一不可）：① UPDATE t_interview SET status=3 WHERE id=? AND status IN (0,1)（失败态也走状态机闸）；② XACK——毒消息也必须 ACK！判死刑=有序放弃，留在 PEL 里它永世 haunting、被反复认领，账本变垃圾场；③ log.error 带全上下文（消息 ID/interviewId/delivery count/最后异常栈）——状态进 DB，证据进日志，各司其职；④ （可选进阶）XADD 一份到死信流留尸检——教学版建议跳过，日志已够。
min-idle-time 算术：一次正常消费 = AI 30-60s，最坏撞 L3 重试翻倍 ≈ 120s。判定"僵尸"的线必须显著大于最长存活时长：取 300s（5 分钟），≈2.5 倍安全系数。定 60s 会怎样？——正在苦干的消费者干活干到一半被 XAUTOCLAIM 抢单，两个消费者同时跑（幸好 H3 挡住了效果，但白烧一次投递计数、多烧一次 SELECT、账本开始失真）。宁可晚救，不可错抢。

### 🔶H5 失败的出口
用户轮询看到 status=3 之后能做什么：开 `/interview/{id}/retry` 重投同一个场次（幂等门怎么配合）？还是只能新发 POST（旧场次留档）？拍板并写清各自的用户故事。
失败出口：拍板 retry 重投同一场次
用户故事 A（retry /interview/{id}/retry）："这场面试是系统搞失败的，用户有权要求重做同一场"——场次 ID 不变、历史不膨胀。幂等门怎么配合？retry 的落地就两步：UPDATE t_interview SET status=0 WHERE id=? AND user_id=? AND status=3（状态机需要一条 3→0 的返工边，合同必须显式画转义表）+ 重投同一个 interviewId 进 Stream。双击防抖白送：第二下点击时 status 已是 0，UPDATE WHERE status=3 影响 0 行→"任务已在进行中"。幂等门不仅防重复消费，也防重复提交——同一个 WHERE 两处受益。
半程脏数据配合项：第一次尝试可能已插入 3 题才死 → 消费者开工时 DELETE FROM t_interview_question WHERE interview_id=? 再全量插——先删后插才是幂等（结果恒为 N 题而不是 N+3 题）。
用户故事 B（只能新 POST）：实现零新增代码，但失败场次变垃圾堆满历史列表，且用户被迫放弃"这场面试"的身份连续性。判 B 有设计罪：把系统故障的成本转嫁给用户的操作成本。

### 🔶H6 上限重开
异步解锁了时长预算——`count` 上限从 5 放宽到几？用 05 合同 §2 的"分布上沿"口径重算一次（385 token/题那个），输出护栏是否跟着改。
上限重开——这里我当场质疑导师的两个口径，先报数再答题
"385 token/题"和 §2.1 实测对不上：回填实测是 45 token/题（completion=225÷5，无 refAnswer）。385 这个数若成立，只能来自"含参考答案"的假设口径——但 R3 已拍板不要 refAnswer。请导师明确 385 的出处；若他意在"评分报告时代会加 refAnswer 产出"（差异化 D 组），那 H6 该按两套口径各算一行，而不是拿旧口径重算。这是传统——上阶段我们被逮了两次口径错，这次轮到我们的数据逮合同里的数，口径冲突必须当面碰平，不许静默采用任何一方。
异步后真正的约束换了维度：时长解锁后，成本（10 题≈0.007 元/次）依然不是瓶颈，新瓶颈是消费吞吐：单线程 30-60s/场，10 个用户同时提交=排队 10 分钟。所以 H6 我的答案：上限 5 → 10（兑现 §2"放宽到 10 的解锁条件=流式改造完成"的承诺），理由不是技术撑不住而是产品口径（一场模拟面 10 题已是 1 小时量）+失控线可见性照旧。max_tokens=3000 保持不动——它的语义是"失控保险费"不是"需求预算"（10×45=450，6 倍余量），除非上面 refAnswer 口径落地才重估。

**导师 R2 修正（你立的规矩，先割到你自己）**：你要求"口径冲突当面碰平"——**采纳，这是本评审最想看到的学员行为**。但碰平之后要用哪头？05 合同 §2.1 有我复测的注记：同端点同配置，你冒烟 completion=225，我复跑 completion=1926（≈385/题）——两个数都真，差在模型当天的表达欲，**385 是分布上沿、45 是下沿**。你 H6 用 45/题推出"6 倍余量、护栏不动"，恰好是你自己点名要反对的"静默采用某一口径"。裁决：上限 5→10 **采纳**（产品论据成立）；护栏按上沿重算——10×385×1.2≈4600 → **max_tokens=5000**。保险费必须盖住最大保额，这不是预算，是承诺。
