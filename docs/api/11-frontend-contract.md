## 0. 技术栈与工程位（已定）
Vue3 + Vite + ElementPlus；独立目录 `frontend/`（与 backend 平级，同仓不同域——G3"目录分引擎"家法的前端版）；
**分工制 #75**：AI 写页面，学员起草页面卡/评审/联调/commit；🔶2 请求层与 🔶3 轮询原语两文件学员亲手写（D1-D2 的硬任务，先写后接 AI 页面）。
联调期后端冻结，接口以 springdoc 文档页为唯一事实。

**TS 纪律（#76 补录）**：全仓 TypeScript 严格模式（strict: true）。所有接口请求/响应一律先定义 interface（DTO/VO 形状以合同与后端 VO 类为唯一事实源），共享类型集中 `src/types/`；**any 必须注释理由**的家法——任何 any 出现处，该行注释写清"为什么这里类型系统给不了/不该给"，无注释的 any 按 bug 处理。
论证（为什么不用 JSDoc 轻量方案）：JSDoc 是注释层约定，编译器不执法——注释说 string、传了 number 照样跑，等于"契约写在纸上没人验票"；本项目接口契约是核心资产（Result<T> 的 code/msg/data 三件全靠类型对齐，F2 映射表查的就是它），类型必须进编译期强制而非可选提示，故 TS 严格模式是底线不是偏好。

## 🔶1. 项目结构：src 下怎么切
目录树你画。必答三问：① API 调用层按后端合同分文件还是按页面分？（提示：01/03/06/07/09/10 六域）② 全局状态（token/用户信息）放哪、活过刷新吗？——这个决定连着 02 合同的存根生命周期，写进你的论证；③ F2 错误码映射表住哪个文件、为什么住那。

① API 调用层怎么分？

拍板：按后端合同分文件。
论证：创建 src/api/ 目录，按域拆分为 auth.ts (01/02)、resume.ts (03)、ai.ts (04/05/08)、interview.ts (06/07)、review.ts (09)、followup.ts (10)。好处是：契约即目录，后端改哪份合同，前端就只动哪个文件，高度解耦。
映射约定（#77，写进 src/api 目录头注释）：**文件按合同域切分，不按 URL 前缀切分**——URL 域与合同域不同构：FollowupController 与 InterviewController 共用 `/interview/**` 前缀，但 10 域的调用落 followup.ts；UserController 的 `/user/**` 跨 01/02 两份合同，同落 auth.ts；`/ai/kb/ask`（08）与 `/ai/chat`（04）、`/ai/questions`（05）同落 ai.ts。目录头注释对照 controller 实枚举（UserController / ResumeController / AiController / InterviewController / FollowupController / ReviewController）落账——骨架提示"六域"本身漏了三域，教训在此：出题人的真相源永远是代码，不是提示。
② 全局状态（token/用户信息）放哪？活过刷新吗？
拍板：放 localStorage，活过刷新。
论证：放内存（如 Pinia）刷新就丢，用户得重新登录。放 localStorage 虽然牺牲了理论上的绝对安全（XSS可读），但符合 JWT 无状态认证的设计初衷（票面可复制），只要做好前端 XSS 防护即可。
③ F2 错误码映射表住哪？
拍板：住在 src/constants/error-map.ts。
论证：它是纯静态常量。独立于组件和请求层，供全局（拦截器、组件内部）统一引用，绝不能散落在各个页面的 if-else 里。
同步机制（#83）：文件头注释标注其对应的 01 码表版本（当前 v0.4：0/1/2/3/400/404/405/500）；"01 合同升版 checklist"增加一条"同步 error-map.ts"——映射表是码表在前端的影子，码表改版影子不跟=静默漂移，对照同步靠 checklist 不靠记性。

## 🔶2. 请求层设计（axios 拦截器）
本节文件=学员手写范围（#75 底线件一）。骨架已钉的家法：401→清态跳登录（F6）；非 0 code→查映射表弹文案（F2）；网络层错误→统一"服务繁忙"兜底。
你亲手补三处：① token 的存放与注入方案（论证：localStorage 与内存的取舍，对着"票面可复制"的既有认知说实话）；② 请求失败的 toast 与业务错误的 toast 要不要同一通道（一句话理由）；③ **页面级 loading 的默认策略**——每个组件自管还是请求层统一计数（08 空手降级案的 UX 镜像）。

① Token 的存放与注入方案
拍板：登录成功存入 localStorage。在 axios 的 request 拦截器中统一注入，且注入前必须过 falsy 守卫（#82）：`if (token) config.headers.Authorization = 'Bearer ' + token`——token 为 null/undefined/空串时不加头，绝不拼出 "Bearer null"。
论证：对着“票面可复制”的认知，JWT 本身就是无状态的，前端存哪都可以被带走。用 localStorage 是为了满足刷新页面不丢失登录态的基本体验。falsy 守卫的理由（8ms 案同族）：过期清理/异常分支让 token 变空值时，无条件拼串会把脏头发给后端，让"没登录"伪装成"登录坏了"，排障方向全歪。
② 失败 Toast 同通道吗？
拍板：同一通道，带一处 carve-out（#78）：**HTTP 401 / code=3 不进 toast**——静默清态跳登录（F6）；其余非 0 code（1/2/400/404/405/500）与网络层错误统一走 ElementPlus 的 ElMessage.error()。
论证：统一通道指**文案出口**统一——所有失败文案都从 error-map 查表产出，来源唯一、文案权不散落；但出口统一不等于行为一律：401 的正确用户动作是重新登录而非读一条红字，弹 toast 反而和跳登录页抢注意力，carve-out 是 F6 差异化处理的正名，不是对统一通道的破坏。原稿"用户无需理解网络层和业务层"作废（#80）：用户确实无需理解，但代码必须区分——F2 与 F6 分居两条路径正是这个区分的落地。
③ 页面级 Loading 策略
拍板：请求层统一计数，但轮询流量不进计数（#79）。计数器三条铁律：① 轮询走独立 axios 实例（或同实例挂 skipGlobalProgress 元数据位，实现时二选一）——轮询 3s 一发若计入全局 requestCount，面试页进度条将永动；② requestCount 的递减收口**三条路径**：响应成功、请求失败（拦截器 error 分支）、请求被取消（abort）——漏任何一条就是只增不减的泄漏（保险丝案同族）；③ requestCount > 0 时展示顶部进度条。
论证：如果让每个组件自管 Loading，代码会极其冗余，页面切换时残留态难清理；统一计数一处实现处处生效——这就是 08 空手降级案的 UX 镜像（网络不通时，全局有感知，而不是页面假死）。轮询隔离的理由是流量语义不同：轮询是"后台心跳"不是"用户等待反馈"，前者不该占用用户的注意力通道。

## 🔶3. 轮询原语（本合同的灵魂页）
本节文件=学员手写范围（#75 底线件二）。F4 三态机的通用化：你要设计**一个**可复用的轮询 hook（interview status / reportStatus / review due 三处复用同一个）。
拍板并论证：① 间隔策略（恒定 3s？退避？上限？）；② 组件卸载/路由切换时的中止语义（fetch 取消还是忽略回调，给理由）；③ 连续 N 次失败的熔断 UX（一直转圈是骗人，直接报错可能误伤——07②门案的后端版）；④ 页面可见性（切标签页暂停？document.visibilitychange）。
**这一节写好，全项目的前端含金量都在这里。**

① 间隔策略
拍板：固定 3s，但连续失败退避（3s → 6s → 12s），上限 3 次。
论证：大模型生成需要时间，3s 是性能与体验的平衡。如果后端挂了，退避能防止前端把后端压死，上限 3 次是防止无脑重试。
② 组件卸载中止语义
拍板：用 AbortController 真实取消在途请求，同时保留 ignoreCallback 兜底（卸载时 abort + 标志位双保险）。
论证（按事实重述，#80）：abort 只是传输层取消，服务端已开始的处理不会因此停下——"abort 是对后端的保护"不成立，原稿论证作废。真实收益两条：① 防回调竞态——慢请求晚到，把过期数据写进已卸载/已换页组件的状态（轮询场景就是旧 status 覆盖新 status）；② 资源整洁——在途连接、挂起的 Promise、定时器句柄随卸载全部释放，不给浏览器留悬空引用。ignoreCallback 仍需保留：abort 掐得住"在途"，掐不住"已到达但回调未执行"的竞态窗口，两者各管一段。
③ 连续 N 次失败熔断 UX
拍板：连续失败 3 次（退避用尽），停止轮询，展示失败态 + 一个**"重试"按钮**：点击复位失败计数并立刻续轮询（#81）——不用"请刷新页面"文案。
论证：一直转圈是骗人（07 门案），静默重试是骗上加骗，报错是唯一诚实选项；但不弹"请刷新"——刷新会丢掉答题页未提交的作答状态，拿用户状态换开发者省事是负收益；"重试"按钮在页面内复位续跑，状态零损失。visibility 从隐藏恢复时同步复位失败计数（#81）：用户切走期间攒下的网络抖动失败，不该由"回来"这一下买单。
④ 页面可见性
拍板：引入 document.visibilitychange，切走时暂停轮询，切回来立刻触发一次并复位失败计数（#81）。
论证（按事实重述，#80）：轮询打的是只读查询接口，"后台拼命发请求烧钱"不成立——烧的是用户设备电量、后端日志行数与 100% 无效的 DB QPS，原稿论证作废。真实理由是资源纪律：用户根本不看这个页面时，每 3s 一发全是浪费；切回立刻触发一次，避免用户"回来后干等 3s 才见第一帧数据"。

## 🔶4. 路由与守卫
未登录可达面：login/register 两页，其余全守卫。拍板：守卫放路由元信息还是全局钩子；401 竞态双弹窗怎么防（两次并发请求同时 401，弹几个）。

守卫放哪？
拍板：用全局钩子 router.beforeEach + 路由元信息 to.meta.requiresAuth。
401 竞态双弹窗怎么防？
拍板：拦截器全局锁 isHandling401，且锁必须有**释放语义**（#81）：第一个 401 置锁→清 token→跳登录；锁在两个时机强制复位——① 跳转登录执行时，② 登录成功写回新 token 时；锁生效期间的后续 401 静默丢弃（与 2② 的 carve-out 同一条通道纪律，不弹 toast）。
论证：用户可能同时发 3 个请求，全部 401 会弹 3 个框，锁住并发是对的；但只有生命周期没有释放的锁是保险丝泄漏案的镜像——用户重新登录后新 token 再遇 401，若残留旧锁，这次的 401 被静默吃掉，用户面对"点了没任何反应"的死寂。锁有生命周期就必须有释放动作，二者缺一不可。
