## 2. 决策点

### 🔶K1 容器与端口
`ai-pgvector`（镜像 `pgvector/pgvector:pg16` 已在本地缓存——那次彩蛋的回收日）。拍板：
a) 端口 **5432 还是 5433**？（`interview-postgres` 那个旧容器禁动但它的端口阴影还在——想清楚"我们是否要永久避开 5432"，给出你的理由）
b) 卷名、密码走 `-e`（不进 Git 老红线）；**新容器出厂自带 `TZ=Asia/Shanghai`**（R9 时钟单源纪律第一次在新容器上的主动执行——别等第二次 qid61 案）。

回答：新容器命名 ai-pgvector，宿主机端口映射 5433:5432，数据卷 ai-pgdata，环境变量强制设置 TZ=Asia/Shanghai。
理由：必须永久避开旧容器的 5432 端口以防冲突；强制设置时区是为了防止 Docker 默认 UTC 时间导致数据库记录慢 8 小时，这是排查日志时的噩梦。密码走 -e，绝不进 Git。

### 🔶K2 双数据源接线（本课墙一，先调研再拍）
Boot 检测到第二个 DataSource 会**罢工自动配置**。方案光谱：
- a) 手工双 Bean：MySQL `@Primary`（喂 MP），PG DataSource 专供向量层（Hikari 自建 + JdbcTemplate/Dao）
- b) PG 侧不用 DataSource Bean，走 pgjdbc `PGSimpleDataSource` 私有对象
- c) dynamic-datasource 全家桶（**过度设计，写出来给我看看你为什么排除它**）
拍板：选哪个+PG 连接参数放哪个配置文件（提示：`application-dev.yml` 的 `spring.datasource` 已被 MySQL 占用）。另答一问：**MySQL 和 PG 之间需要事务一致性吗？**（答"要"的先想清楚要在哪一步——这题答对省你三天弯路。）

选择方案a，"为什么不用 dynamic-datasource？"→ 我们没有运行时切库需求，是静态的两库分工； "为什么不只把 PG 当外部资源？"→ 连接池生命周期、配置注入、可测试性都会变差； "@Primary 起什么作用？"→ 按类型注入的唯一裁决。
MySQL和PG之间不需要事务一致性，因为PG是只读记忆体，写PG的的管线与写MySQL的业务链在时间、入口和代码上都完全分离，不存在需要两库原子提交的单一业务动作。

### 🔶K3 embedding 选型（本课第一次多厂商动真格）
DeepSeek 无 embedding 接口——#10 你们自己预言的"多 key 并存"落地日。候选：
- a) 百炼 `text-embedding-v3/v4`（OpenAI 兼容 embeddings、1024 维、价格查当日牌价——**调研义务：报数字**）
- b) 本地开源模型（bge 类，经 ollama 或纯 Java 推理）——token 零费换内存/延迟成本
- c) 其他你在文档里发现的第三方
拍板表格式：单价×题池规模=一次性成本；查询侧每场面试调用数×单价=运行成本；延迟预算。**环境变量名沿用 R10 口径（厂商前缀合法）：`BAILIAN_API_KEY` 与 `DEEPSEEK_API_KEY` 并存。** 维度必须与表 schema 锁死（写进 K4）。

选百炼 text-embedding-v4，维度锁 1024。
理由三点：
维度选项更全：v4 支持 2048/1024/768 等，未来如果你想把维度升到 1536 做更细的语义区分，不用换模型，只改建表参数；v3 最高只有 1024。
单题容量更大：v4 单行最大 8192 Token，一道长面试题加解析完全塞得下；v3 只有 128 Token，长题会被截断。
成本可忽略：2000 题一次性成本约 0.15 元，查询侧几乎免费，完全不需要为了省钱引入本地模型。
环境变量沿用文档要求：BAILIAN_API_KEY 与 DEEPSEEK_API_KEY 并存，百炼 key 走 embedding，DeepSeek key 走 chat 生成。

### 🔶K4 题池 schema 与审核流（本课墙二：PgVectorStore 托管 vs 自建）
两条实现路线：
- **托管**：Spring AI `PgVectorStore`（自带 schema：id/content/metadata/embedding，跑初始化 DDL）+ SimpleraritySearch 全家桶——省事，但**元数据是弱类型 Map**，"审核状态"这种业务字段靠约定
- **自建**：自己的表（建议列：content/category/difficulty/status(draft→pending→approved→retired)/source/embedding vector(N)/embedding_model/时间戳）+ HNSW 或 ivfflat 索引（**拍板二选一并给理由**）+ 手写相似度 SQL
拍板：路线、表名、维度（=K3）、索引类型、以及**审核状态机**——重点答：**运行时检索必须只命中 approved，这条硬约束写在哪一层？**（提示：这就是 RAG 投毒的第一道闸；写漏一层=把审核制变成装饰品）
入库管线（本版本）：离线脚本批量灌样题（生成走现有 LLM+人工改稿标记 approved），**不做管理 HTTP 端点**（K7 解释为什么这是安全而非偷懒）。

答 1：路线 → 自建表
理由按重要性排：
审核闸需要强类型字段，metadata 袋撑不住。 安全攸关的 status 必须享受数据库约束：NOT NULL + CHECK (status IN ('draft','pending','approved','retired'))。放进托管的 JSON 袋里，拼写错误不报错、值域无人看管——等于把门锁装在橡皮泥上。
检索逻辑就一条 SQL，手写的"债务"几乎为零。 K4 那层的 <=> + ORDER BY + LIMIT，一个 DAO 方法装得下。托管省掉的工作量，在你们的规模下本来就不多。
数据质量要能用肉眼查。 审核是人工环节，Navicat 打开一列列真字段抽查，比解析 JSON 文本友好太多。
代价（文书里要如实写）：自己维护建表 DDL 和那条检索 SQL——就这两条，都小到可接受。
答 2：索引 → 本期不建，写明阈值后补 HNSW
暴力扫描的真实成本：几万行 × 1024 维余弦运算 ≈ 几十毫秒级——在你们 topK 检索的延迟预算里根本不排第四位（大头永远是 embedding 模型调用那一次网络往返）。
ivfflat 排除：空表/小表建不了（要先训练聚类），精度还要调 probes——买一个用不上的麻烦。
文书里这样落："行数 < 10 万不建索引；到阈值后 CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)，与余弦运算符配套，建完用 V4 基线回归验证检索质量无回退。" 有数字、有语法、有验证——这比硬选一个都正确。
答 3：审核闸在哪层 → SQL 层 + 出口收敛，写成一条纪律
具体方案，三层各安排一个角色：
text
主闸：检索 SQL 里 WHERE status = 'approved' 写死为常量
      ——不是参数，任何调用方都改不了它。
门框：全项目能执行这条 SQL 的出口收敛为一个类
      （如 KnowledgeSearchDao），并立规：别的代码不许绕过它碰 kb_question 读。
写侧：CHECK 约束管住入库值域（draft 才能进，approved 靠审核脚本改）——
      它不防"读到未审内容"，防"垃圾状态混进来"。
为什么"SQL 层+单出口"算硬约束：投毒要生效，得让未审内容被读出来；而读只有那一条 SQL，条件又是代码常量不是入参——攻击路径变成"得先改代码再发版"，那就不是运行时风险而是代码审查范围了。托管路线做不到这条，正因为它的 filter 是调用方传的——这反过来也支撑了答 1 选自建。

### 🔶K5 检索参数与出处
topK=？阈值=？过滤=category+difficulty 元数据先行还是纯向量？——拍板并**全部做成配置**（不许硬编码，理由：调检索参数是日常调参不是发版）。
**出处回显**：RAG 化的出题接口返回 `evidenceKbIds`（引用了题池哪些条目）——延续 05 model/usage 可观测衣钵：AI 的回答要能考古。
topK 和 阈值（Threshold）选多少？
topK = 3：召回最相似的 3 道题作为参考上下文。选 3 是因为面试题通常较短，3 道题足以覆盖核心知识点，同时不会撑爆大模型的上下文窗口（节省 Token）。

相似度阈值 = 0.75：（通常用余弦相似度，范围 0-1）。低于 0.75 的题，说明跟用户问的根本不是一回事，直接丢掉。这能极大减少 AI 幻觉。
2. 过滤策略：元数据先行还是纯向量？
拍板：元数据先行（Pre-filtering）！
理由：如果你的题库里有 1 万道题，包含 Java、前端、产品等。用户明明是面 Java，如果不加过滤直接做纯向量搜索，可能会把“前端的闭包”搜出来（因为它们在向量空间里可能很近）。必须先在 SQL 层用 WHERE category = 'Java' AND difficulty = 'hard' AND status = 'approved' 强过滤，然后再在这部分数据里做向量距离排序。
3. 全部做成配置（不许硬编码）
原因：你以后跑真实数据时，大概率会发现 0.75 太严了（搜不出东西），或者 topK=3 太少了，你每天都在微调。如果写死在 Java 代码里，每次都要重启服务发版。必须放到 application.yml 里！
4. 出处回显（evidenceKbIds）
接口必须返回这个 AI 的回答参考了题库里的哪几道题（把题目的 ID 或标题返回）。这叫“AI 的可观测性”，用户点一下就能看到原始出处，不用怕 AI 瞎编。

### 🔶K6 RAG 接到哪一端（本课的产品判断）
候选：a) 出题链（检索相似题→模型改编/参照生成，题题有出处）；b) 评分链（八股题给评分器递知识库标准答案=J4 测量口径的第一步）；c) 两端都做；d) 本阶段只做"知识库问答端点"（新 `/ai/kb/ask`，独立最小链，出题评分链暂不动）。
**推荐你认真考虑 d 作起点**（理由要你写：改动面/回滚成本/05 和 07 合同要不要跟着升版）——但反推荐也可以，带论证来。

选 d，理由三层：05/07 零升版（合同稳定）；旧回归网零重跑（测试稳定）；检索调参需要独立试验场（工程质量）。a/b 作为 d 成熟后的第二步，届时再立升版草案。 反过来说，如果哪天你确实要抢"评分口径"这个产品价值，也应该等 V4 基线证明检索靠谱之后再接 b——顺序本身就是论证。

### 🔶K7 权限面（今天最小，把债记清）
题池审核脚本谁能跑？（现在=运维本人/学员本机，无 HTTP 面=无攻击面——这就是"不做管理端点是安全设计"的完整句子）。**若**你 K6 选了含端点方案涉及写操作：权限模型三选一（白名单 userId 配置/`t_user` 加 role 列+拦截/推迟）——且注意 **403 错误码还不存在于 01 文档表**，引入即触发新一轮契约变更（错误码"禁止私加"的家法你还记得）。

回答：不开任何管理写端点，题库导入走本地离线脚本。
理由：无 HTTP 面 = 无攻击面。直接用本地脚本灌数据，彻底规避了复杂的鉴权设计（无需改 t_user 表，无需引入 403 错误码），防止黑客通过接口进行 RAG 投毒。未来要做“用户自定义喂题库”，等核心链跑通后再加 tenant_id 做多租户隔离。

## 5. 导师评审裁决（2026-11-14）

**K1 ✅ 批准。** 5433 永久避让成立（禁动 ≠ 永不存在）；**TZ 主动配置是 R9 纪律第一次自我复制**——纪律长出新枝，这句可进简历"工程文化"。

**K2 ✅ 满分。** 三问答全对。一致性题的完整版给你补一句：因为写管线分离，**PG 侧根本不存在需要回滚的业务事务**——异常处理里也不要有"补偿向量写"的冲动，没有东西要补偿。`@Primary=按类型注入的唯一裁决` 表述精准。

**K3 ✅ 批准，一处红笔。** "v3 单条 128 token"疑似记忆偏差（官方口径 2048）；选型方法论与成本算式都对，但**牌价数字以 V6 实测回填为准**——R2 的家法：数字进文件，不进印象。维度=表schema=模型三锁逻辑保留。

**K4 ✅ 全场最佳。** "门锁装在橡皮泥上"的比喻、三层闸（SQL 常量主闸/单 DAO 出口门框/CHECK 写侧）、索引阈值条款带语法带验证——此段达到公司内评审提交水准。两句 house keeping：ivfflat 排除理由正确；"单出口"这条纪律靠 V2 看门，不靠自觉。

**K5 ⚠️ 两案，先认账再裁决：**
- **E1 分类学纠正（骨架自己埋的坑，导师认）**：K5 原文"category+difficulty 先行过滤"把 trap 写在了题面上——category 是**题型**枚举（八股/项目/场景/HR），不是技术方向。你"过滤 Java"的回答恰好把 trap 暴露成了需求。**裁决：`kb_question` 增加 `tags text[]`（技能标签轴）**；元数据预过滤 = tags（方向）+ difficulty + status，category 维持四值对齐 05（出题时分配题型）。两轴不许混用——这是"幽灵字段"第三次现形，前两次（experience、status）是学员编列，这次是题面埋雷，教训同构：**任何过滤维度先问它属于哪条轴**。
- **E2 阈值语义**：pgvector 的 `<=>` 返回余弦**距离**（=1−相似度）。"相似度 0.75"翻译成 SQL 是 `distance < 0.25`。配置项若叫 `similarity-threshold=0.75` 而 SQL 比的是距离，语义分叉只是时间问题。**裁决：配置术语就叫 `distance-max=0.25`**，与运算符同向诚实命名，换算只在 DAO 一处——单一事实源又赢一次。

**K6 ✅ 采纳，且你的论证比我的推荐理由更完整**（合同稳定/测试稳定/调参试验场；"顺序本身就是论证"可原话引用）。b 端接入的前置（V4 基线证明检索靠谱）记录为第二步立项条款。

**K7 ✅ 批准。** "无 HTTP 面=无攻击面"句子完整；tenant_id 不做提前设计=克制正确。**但补一刀：d 方案的 `/ai/kb/ask` 是读端点、不写库，攻击面仍在——query 是用户输入，材料是知识库内容，两头都是数据。J5 五层防线必须原样平移（E3：candidate_query 定界 + 枚举/结构硬校验 + evidenceKbIds 出处回显），这不是 K7 的尾巴，是 ask 链的开工前置件。**

**实现注意清单（开工时落 DDL/SQL/配置）**：E1 tags 双轴进 sql/05；E2 distance-max 命名进配置；E3 ask 链走 J5 纵深。
