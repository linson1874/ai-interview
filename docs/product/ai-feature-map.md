# AI 能力地图与模块边界 v1.0（产品讨论归档 2026-11-06）

## 1. 一句话回答核心疑问

**"根据简历出题"和"基于 RAG 知识库出题"是同一条流水线的两种"上下文来源"，不是两个平行系统，也不是二选一。**

```
上下文来源提供者          组装与生成的公共流水线（本项目的 AI 心脏，只有一条）
┌──────────────┐
│ A. 简历(t_resume) │──┐   ┌────────────┐   ┌───────────┐   ┌──────────────┐
└──────────────┘   ├──▶│ Prompt 组装器 │──▶│ ChatClient │──▶│ 结构化输出Converter │──▶ 题目JSON
┌──────────────┐   │   └────────────┘   │(可路由多模型)│   └──────────────┘
│ B. 八股库(pgvector│──┘        ▲
│   向量检索topK)  │            └─ system prompt(角色/规则/格式)
└──────────────┘
     ▲ Day8 只接 A；阶段四接 B；最终形态 = A+B 混合出题（真实面试官就是这么干的）
```

## 3. 关键澄清（对学员问题的直接回应）

1. **"上传简历后 AI 分析再出题"是流程终态没错，但当前"上传"环节是空心的**：现在简历靠用户按合同 03 的结构化表单填（`t_resume` 字段即上下文来源 A）。"上传 PDF→AI 抽取→自动填表"是第 5 项能力，不是出题的前置条件。
2. **Day8 出题不需要等 RAG**：大模型自身通识足以基于"Spring Boot、MySQL 索引"这些标签出合理八股题+项目深挖题。RAG 解决的不是"能不能出题"，而是**"题与答案是否可溯源、是否符合你自己知识库的口径、以及不随模型版本漂移"**——这是第 4 项能力的价值，也是它独立存在的原因。
3. **同一个功能模块吗？**——业务上是两个功能（不同的用户故事），技术上是一个模块（同一条"组装→调用→结构化"流水线）加两个可插拔的上下文提供者。05 合同的接口设计应留缝不建墙：`QuestionContext`（当前只有简历实现）将来加 `RagContext`，**Day8 不许提前抽象建墙**（过度设计警告），只要求组装逻辑收口在一个方法里。

## 4. 对当下决策（合同 05）的影响

- Q1b"没简历能不能出题"→ 有了本地图，答案更好选：**本版不能**（上下文来源 A 是唯一输入；"只按岗位出通用题"= 无锚定的通识出题，质量不可控且和简历功能抢坑——留阶段五再议）。
- Q3 refAnswer → 结合 2/4 看：出题时带参考答案=为评分(能力2)存料，但会翻倍成本；折中方案（生成题时 refAnswer 可空，评分阶段按需二次生成）留给拍板讨论。
- 阶段三的异步化改造对象 = 本图第 1 行的流水线：Stream 只是把"同步等待"换成"任务提交+轮询/推送"，心脏不变。
